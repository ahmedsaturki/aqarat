# دليل النسخ الاحتياطي والاستعادة لمنصة Aqarat

**الحالة:** مسودة تشغيلية جاهزة للمراجعة قبل اعتمادها في الإنتاج  
**النطاق:** Supabase/PostgreSQL، migrations، إعدادات Vercel، تكاملات Telegram وGemini، وبيانات التشغيل  
**القاعدة الأساسية:** لا تُنفذ استعادة أو حذف أو overwrite على الإنتاج من خلال هذا الدليل دون موافقة تشغيلية صريحة وسجل تغيير قابل للمراجعة.

## الهدف ومستوى الحماية

يهدف هذا الدليل إلى جعل بيانات Aqarat قابلة للاستعادة بعد فقد بيانات، خطأ migration، فساد تكامل، أو تعطل بيئة التشغيل. يجب اعتبار النسخة الاحتياطية غير صالحة للاعتماد عليها حتى يتم اختبار استعادتها في بيئة معزولة والتحقق من سلامة العلاقات والـ RLS والـ jobs والتدقيق.

| العنصر | المستوى المطلوب قبل Pilot | المستوى المطلوب قبل GA |
|---|---:|---:|
| RPO لبيانات التشغيل | 24 ساعة كحد أقصى | يحدد تعاقديًا ويُختبر دوريًا |
| RTO للبيئة | يوم عمل واحد | يحدد تعاقديًا ويُختبر دوريًا |
| اختبار restore | مرة قبل Pilot | دوريًا، وبعد كل تغيير كبير |
| احتفاظ بالنسخ | 7 نسخ يومية على الأقل | سياسة احتفاظ معتمدة ومشفرة |
| تشفير النسخ | إلزامي | إلزامي مع إدارة مفاتيح موثقة |
| تسجيل العملية | إلزامي دون أسرار | إلزامي مع evidence ونتيجة تحقق |

القيم السابقة هي **أهداف تشغيلية أولية وليست اتفاقية مستوى خدمة**. يجب اعتمادها من مالك المنتج قبل إعلانها التزامًا تجاريًا.

## ما يجب نسخه

يجب فصل نسخة البيانات عن نسخة البنية والإعدادات. نسخة البيانات تشمل الجداول والعلاقات والفهارس والـ enums والدوال والـ RLS والسياسات، مع استبعاد أي مفاتيح سرية. نسخة البنية يجب أن تتضمن migrations الموجودة في المستودع، ونتيجة تصدير تاريخ migration من أداة قاعدة البيانات عندما تكون متاحة. أما إعدادات التشغيل فتشمل أسماء المتغيرات المطلوبة فقط وقيمًا سرية محفوظة في مدير أسرار معتمد، وليس داخل ملفات النسخ أو logs.

| الفئة | المحتوى | ممنوع تضمينه |
|---|---|---|
| PostgreSQL | schema، data، indexes، functions، policies | كلمات المرور والمفاتيح داخل ملف غير مشفر |
| migrations | ملفات SQL وmanifest وحالة التطبيق | تعديل التاريخ لإخفاء migration فاشلة |
| Vercel | أسماء المتغيرات، domains، rewrites، deployment metadata | قيم الأسرار في Git أو artifacts عامة |
| Telegram | webhook contract واسم السر ومعلومات القناة التشغيلية | raw tokens أو رسائل خاصة غير لازمة |
| Gemini | اسم التكامل وحدود الاستخدام وhealth contract | API key أو prompts تحتوي بيانات شخصية |
| CI/CD | workflow definitions ونتائج checks | environment dumps أو masked secret output |

## دورة النسخ الموصى بها

تُنفذ النسخ التلقائية خارج request path وبحساب least-privilege. يجب أن تكون العملية idempotent، وأن تكتب artifact مشفرًا باسم يحتوي على timestamp وcommit أو migration marker، ثم تتحقق من الحجم وchecksum وإمكانية القراءة دون تسجيل محتوى البيانات. إذا فشلت النسخة، يجب إرسال تنبيه bounded دون إعادة محاولة غير محدودة أو طباعة connection string.

يجب أن يكون فشل النسخ مرئيًا وقابلًا للتصعيد. لا يجوز اعتبار وجود ملف في التخزين دليلًا على صلاحية النسخة؛ الدليل المطلوب هو نجاح checksum ونجاح فحص restore أو verify دوري.

## إجراء restore آمن

### قبل الاستعادة

يُفتح change record يوضح السبب، النسخة المستهدفة، نقطة الزمن، RPO/RTO المتوقعين، صاحب الموافقة، وخطة الرجوع. تُجمّد migrations والـ workers التي قد تكتب إلى قاعدة البيانات، ويُؤخذ snapshot إضافي من الحالة الحالية إن كان ذلك مدعومًا. لا تبدأ الاستعادة إذا كانت هوية النسخة أو سلامة checksum غير مؤكدة.

### الاستعادة في بيئة معزولة

تُستعاد النسخة أولًا إلى مشروع أو قاعدة بيانات غير إنتاجية. بعد ذلك تُنفذ اختبارات schema وforeign keys وRLS والسياسات والدوال، ويُتحقق من أن `audit_events` append-only وأن حالات jobs والـ leases متسقة. يجب تشغيل اختبارات التطبيق، release contract، deep health، واختبار worker محدود دون إرسال رسائل خارجية.

### قرار الترقية إلى الإنتاج

لا تتم الاستعادة الإنتاجية إلا بعد مقارنة counts الأساسية، آخر timestamps، عدد jobs غير النهائية، وعدد audit events بين المصدر والنسخة. يجب توثيق الفروقات المقبولة صراحة. إذا فشل أي تحقق، تُوقف العملية ولا يُجرى repair يدوي واسع على الإنتاج.

### بعد الاستعادة

تُعاد الأسرار من مدير الأسرار دون طباعتها، وتُراجع rewrites وenvironment bindings، ثم تُشغل health checks وproduction contract وauthenticated deep health. يُراقب queue lag وerror rate وSupabase response time والتكاملات الخارجية. لا يُعاد تفعيل jobs أو outbound publishing قبل إثبات عدم وجود duplicate processing أو رسائل مكررة.

## تحقق البيانات بعد الاستعادة

| الفحص | معيار النجاح |
|---|---|
| schema | جميع migrations المعتمدة موجودة أو موثق سبب اختلافها |
| العلاقات | لا توجد foreign-key violations جديدة |
| الأمن | RLS مفعّل، policies موجودة، ولا توجد grants عامة غير مقصودة |
| التدقيق | append-only guard فعال، وcorrelation IDs قابلة للتتبع |
| العمال | jobs العالقة قابلة لإعادة الالتقاط، والـ leases المنتهية تُعاد بأمان |
| البيانات | counts وtimestamps والعينات الحرجة متطابقة أو مفسرة |
| التطبيق | unit وrelease وdeep-health ناجحة |
| التكاملات | لا يوجد إرسال خارجي غير مقصود أثناء الاختبار |

## اختبار restore الدوري

ينبغي إجراء restore drill في بيئة معزولة على فترات تعتمدها الإدارة، وبعد كل migration كبيرة أو تغيير في مخطط البيانات. يحفظ الاختبار evidence يتضمن version، checksum، وقت البداية والنهاية، RPO/RTO الفعليين، نتائج الفحوصات، والفروقات. تُحذف البيئة المؤقتة فقط بعد حفظ evidence وعدم وجود حاجة تشغيلية لها، مع توثيق الحذف.

## حدود الأتمتة الحالية

يمكن أتمتة التحقق من وجود ملفات migrations، سلامة SQL syntax، غياب الأسرار من artifacts، وجود إعدادات البيئة بأسماءها، ونجاح release checks. أما إنشاء نسخة إنتاجية فعلية، تخزينها خارج المستودع، أو تنفيذ restore إنتاجي، فيتطلب صلاحيات تشغيلية وموافقة مستقلة وإدارة أسرار مناسبة. لا ينبغي وضع هذه العمليات داخل Vercel Hobby request path أو تشغيلها على كل deployment دون سياسة احتفاظ وحدود تكلفة.

## قائمة اعتماد قبل GA

| البند | الحالة الحالية | الإجراء المطلوب |
|---|---|---|
| advisor الأمني في Supabase | لا توجد lints في آخر فحص read-only | إعادة الفحص بعد أي migration |
| migrations المحلية | موجودة في المستودع | الحصول على export تاريخي موثوق ومقارنته بالـ manifest |
| restore drill | غير مثبت كاختبار إنتاجي دوري | تنفيذ drill معزول وتسجيل RPO/RTO الفعليين |
| تخزين النسخ | يحتاج اعتماد backend وسياسة retention | اختيار تخزين مشفر وصلاحيات least-privilege |
| runbook | أُنشئ هذا الدليل | اعتماد المالك وتعيين on-call ومسؤول موافقة |
| الأسرار | محمية من Git والسجلات | مراجعة التدوير والاستعادة من مدير الأسرار |

> لا تعتبر Aqarat جاهزة للاعتماد التجاري الكامل حتى ينجح restore drill موثق، وتُثبت سلامة البيانات والتكاملات بعده، ويُعتمد مسار موافقة واضح للاستعادة الإنتاجية.
