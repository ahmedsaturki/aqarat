# تصميم الهوية والصلاحيات متعددة المستخدمين

## القرار المعتمد

تعمل لوحة Aqarat حاليًا بجلسة موقعة محليًا مشتقة من `DASHBOARD_ADMIN_SECRET`، وتستخدم مفتاح خدمة Supabase للوصول الخلفي مع سياسات RLS تمنع الأدوار العامة من القراءة والكتابة المباشرة. هذا مناسب كحاجز أولي لكنه لا يوفر هوية فردية أو فصلًا بين المشاهدة والتنفيذ أو إدارة دعوات وإلغاء جلسات.

سيتم الانتقال تدريجيًا إلى نموذج متعدد المستخدمين دون إزالة المسار الحالي في الإصدار الأول. المسار الجديد يعتمد على **Supabase Auth** لتوثيق المستخدم، وعلى جداول تطبيقية مستقلة للصلاحيات، بينما يبقى مفتاح الخدمة داخل الخادم فقط. لا يعتمد التفويض على بيانات يرسلها المتصفح، بل يحل الخادم هوية الجلسة ثم يجلب الدور والصلاحيات من قاعدة البيانات.

## الأدوار الأولية

| الدور | القراءة | الإجراءات التشغيلية | إدارة المستخدمين والسياسات |
|---|---|---|---|
| `owner` | كل نطاقات لوحة التشغيل | كل الإجراءات الحساسة | نعم |
| `admin` | كل نطاقات لوحة التشغيل | إجراءات المراجعة والطوابير والعملاء والمصادر | إدارة المستخدمين دون تغيير سياسة المالك |
| `operator` | التشغيل والعقارات والعملاء والمراجعة | إعادة المحاولة وتحديث حالة العميل والمراجعة | لا |
| `analyst` | القراءة والرؤى والتدقيق المسموح | لا توجد كتابة تشغيلية | لا |
| `viewer` | القراءة المحدودة | لا توجد كتابة | لا |

الدور الافتراضي للمستخدم الجديد هو `viewer`، ولا يمنح أي صلاحية كتابة تلقائيًا. إنشاء أول `owner` يتم عبر عملية تهيئة موثقة ومحمية، وليس عبر تسجيل عام.

## نموذج البيانات الإضافي

سيُضاف بشكل additive فقط: `workspace_members` لربط مستخدم Supabase Auth بالمساحة والدور وحالة العضوية، `workspace_invitations` لدعوات محدودة العمر ومستهلكة مرة واحدة، `dashboard_sessions` لتتبع الجلسات وإبطالها، و`permission_catalog` و`role_permissions` لتعريف الصلاحيات صراحة. لا تُحذف جداول البيانات الحالية ولا تُعدّل سجلاتها عند تطبيق migration التأسيسي.

تُخزن مراجع المستخدمين كـ UUID من `auth.users`، ولا تُخزن كلمات المرور أو رموز الدخول في جداول التطبيق. رموز الدعوة تُعرض مرة واحدة عند الإنشاء، وتُخزن في قاعدة البيانات على هيئة digest فقط. جلسات Supabase Auth تبقى مصدر إثبات الهوية، بينما يسجل التطبيق جلسة تشغيل قابلة للإبطال مع `revoked_at` ووقت انتهاء ووسوم تدقيق غير حساسة.

## حدود التفويض

تُحوّل مسارات لوحة التحكم إلى حارسين منفصلين: `requireDashboardIdentity` للتحقق من هوية الجلسة، و`requirePermission` للتحقق من الصلاحية المطلوبة. القراءة لا تمنح الكتابة ضمنيًا. إجراءات `review_approve`, `review_reject`, `job_retry`, `publication_cancel`, `discovery_toggle`, و`lead_status` تُربط بصلاحيات منفصلة، ويُسجل كل نجاح أو رفض في `audit_events` مع actor UUID ونوع القرار وسبب مختصر.

المسار القديم يستمر مؤقتًا باعتباره حساب تشغيل legacy وحيدًا بصلاحيات `owner`، مع وسم واضح في سجل التدقيق. لا يُسمح للمسار القديم بإنشاء مستخدمين أو دعوات؛ إدارة الهوية يجب أن تتم من المسار الجديد بعد تهيئة أول مالك. بعد إثبات الاستخدام الناجح وإكمال التحقق الإنتاجي يمكن إصدار PR مستقل لإيقاف legacy، ولا يتم ذلك تلقائيًا.

## الضوابط الأمنية

يجب فرض same-origin على عمليات تسجيل الدخول والدعوات، واستخدام cookies آمنة و`HttpOnly` و`SameSite=Strict`، وتحديد مدة انتهاء قصيرة مع تجديد صريح. يجب تطبيق rate limit على محاولات الدخول والدعوات، والتحقق من البريد عبر Supabase Auth، وإبطال الجلسات عند تعطيل العضوية أو تغيير الدور الحساس. يجب ألا تظهر رسائل Supabase الخام أو رموز الدعوة أو البريد الكامل في السجلات؛ تمر الأخطاء عبر `safeErrorMessage` وتُسجل معرفات correlation فقط.

تُراجع migration قبل تطبيقها على الإنتاج، ثم تُشغّل اختبارات RLS ورفض الوصول المباشر، وتُعاد فحوصات Supabase Security وPerformance Advisor. لا تُنفذ أي عملية backfill أو حذف قبل وجود دليل من قاعدة الإنتاج ولقطة backup حديثة.

## خطة التنفيذ

الخطوة الأولى هي إضافة migration تأسيسية للجداول والفهارس والسياسات الافتراضية دون ربط المسارات الحالية بها. ثم تضاف طبقة resolver واختبارات وحدات لعقود الصلاحيات. بعد ذلك تُضاف مسارات الدعوات والإدارة وتُحرس الإجراءات الحالية تدريجيًا. كل خطوة مستقلة في PR مع CI، وتُطبق migration على بيئة staging أو dry-run أولًا، ثم يتم التحقق من الإنتاج قبل الانتقال للخطوة التالية.
